# Day 15 — Caching: cache-aside, invalidation, stampedes, TTL strategy
*Week 3: Data at scale (Register A: your LinkedIn war stories) · ~60 minutes · 2026-10-19*

**Why this matters in a founding-engineer interview** — Caching is the first lever everyone reaches for and the source of the most confusing production bugs (stale data, stampedes, cold-start outages). Interviewers use it to see whether you add a cache because a measurement told you to, and whether you know how it fails. The founding-engineer signal: "I'd delay a cache until the DB is the proven bottleneck, and when I add one I'll already have an answer for invalidation and for the cold-start herd."

## 1. Primer (10 min)

A cache trades **freshness and simplicity** for **latency and load reduction**. Every cache is a second source of truth that can be wrong; the design question is *how wrong, for how long, and who notices*.

Vocabulary:
- **Hit ratio** — hits / (hits + misses). Average read cost = `h·t_cache + (1−h)·t_origin`. At 90% hit the origin still sees 10% of traffic; going 90→99% cuts origin load 10×, which is why the last few points matter most.
- **Cache-aside (lazy loading)** — app checks cache; on miss reads DB, writes cache. The default. App owns all logic.
- **Read-through** — cache library/proxy loads on miss. Same behaviour, logic lives in the cache layer.
- **Write-through** — write goes to cache and DB synchronously. Fresh reads, slower writes.
- **Write-behind (write-back)** — write to cache, flush to DB later. Fast, but you can lose data. Rarely right at a startup.
- **TTL** — time-to-live; the cheapest invalidation strategy ("it's wrong for at most N seconds").
- **Stampede / thundering herd / dogpile** — many concurrent misses on one key all hit the origin.
- **Negative caching** — caching "not found" so nonexistent keys don't hammer the DB.
- **Hot key** — one key taking disproportionate traffic (one cache node saturates even if the cluster is idle).

```
 cache-aside read                         write path (invalidate, don't update)
 ─────────────────                        ──────────────────────────────────────
 app ──GET k──► cache ──hit──► return     app ──UPDATE──► DB
          │                                 │
          └─miss─► DB ──► SET k (TTL) ─►    └──DEL k──► cache   (next read repopulates)
```

Layers you can cache at, cheapest first: HTTP/CDN (`Cache-Control`, ETag) → in-process (dict/LRU) → shared (Redis/Memcached) → DB itself (Postgres shared_buffers, materialized views).

## 2. Deep dive (25 min)

### 2.1 "5 users, ship in 2 weeks": probably no cache
Rough, order-of-magnitude numbers (estimates; vary with hardware and network): Redis GET in the same AZ ≈ 0.2–1 ms; Postgres primary-key lookup with warm buffers ≈ 0.3–2 ms server-side, 1–5 ms with network and ORM; an uncached "dashboard" query with joins can be 50–500 ms. A single modest Postgres handles thousands of simple reads/sec.

So for v1:
1. **Fix the query first**: index, kill N+1s, `EXPLAIN ANALYZE` (Day 3). Most "we need a cache" is a missing index.
2. **HTTP caching is free**: `Cache-Control: public, max-age=…` on static and public data; ETag/`If-None-Match` for the rest. A CDN in front of your Next.js app solves a startling share of load.
3. **In-process cache** for tiny, slow-changing, read-everywhere data (feature flags, plan config, instrument master). In Python: `functools.lru_cache` or a dict with a timestamp. No network hop, no new infra. Cost: each process has its own copy, so staleness differs across instances.
4. Only then **Redis**, when you can name the query/endpoint, its QPS and the DB metric that justifies it. Redis is also another thing to run, monitor and secure; founders often already need it for queues/rate limits (Days 4, 6), which lowers the marginal cost.

### 2.2 Cache-aside, done carefully

```python
async def get_user(uid: int) -> dict | None:
    key = f"user:v3:{uid}"            # version in key: schema change = new namespace
    if (raw := await redis.get(key)) is not None:
        return None if raw == b"__NONE__" else json.loads(raw)
    row = await db.fetch_user(uid)
    if row is None:
        await redis.set(key, b"__NONE__", ex=30)           # negative cache, SHORT TTL
        return None
    await redis.set(key, json.dumps(row), ex=300 + random.randint(0, 60))  # jittered TTL
    return row

async def update_user(uid, fields):
    await db.update_user(uid, fields)   # commit first
    await redis.delete(f"user:v3:{uid}")  # then invalidate
```

Details that matter:
- **Delete, don't set, on write.** Setting the new value from the writer creates races (two writers' cache sets can land in the opposite order of their DB commits → stale value cached until TTL). Deleting is idempotent and safe.
- **Still racy, though.** Classic interleaving: reader misses → reads old row from DB → writer commits and deletes key → reader sets the *old* value. Stale until TTL. Mitigations: short TTL as a backstop (always have one), versioned values (`SET` only if version ≥ existing, via Lua/WATCH), or accept it. Facebook's memcache paper handles this with "leases" — worth knowing exists; you almost never need it at <100k QPS.
- **Failure of the cache must not be failure of the app.** Wrap cache calls with a tight timeout (e.g. 20–50 ms) and fall through to the DB — and then think about what happens when the DB suddenly takes 100% of traffic (see 2.4). Tie back to Day 9: the cache is a dependency; give it a circuit breaker.
- **Cache DTOs, not ORM objects**, and put a schema version in the key. Deploying new code that can't deserialize old entries is a classic mid-deploy incident.
- **Serialization cost is real**: JSON-encoding 50KB per hit at 5k QPS is real CPU. Measure before assuming Redis is "free".

### 2.3 Invalidation: the options ranked by how much they cost you

| Strategy | Staleness | Complexity | Use when |
|---|---|---|---|
| TTL only | up to TTL | trivial | Almost everything in v1: profiles, counts, lists |
| Delete-on-write (same code path) | ~0 except race window | low | You own all writers; single service |
| Event-driven invalidation (outbox/CDC → delete) | seconds | medium | Many writers, multiple services (ties to Day 6 outbox) |
| Versioned keys / generation counters | 0 for those readers | medium | Invalidating *groups* ("all of org 7's lists"): bump `org:7:gen`, include in keys; old keys expire by TTL |
| Write-through | ~0 | medium | Read-heavy, write path can afford latency |

"There are only two hard things…" is a joke because **you can't enumerate every query that depends on a row.** The fix is not cleverness; it's reducing the number of cached shapes (cache entities by ID, compose in the app) and using TTLs as the safety net. Cached *lists/aggregates* are where invalidation gets nasty — prefer short TTLs or generation counters there.

**Decide staleness per use-case, with the product owner.** Profile name: 5 min fine. Account balance shown after a transfer: not fine (read-your-writes — Day 16). Price in a checkout: never cached past the moment of charge.

### 2.4 Failure modes (this is the interview section)

**Stampede on a hot key.** A popular key expires; 2,000 concurrent requests miss; all 2,000 run the expensive query. DB saturates, queries slow, more requests pile up, nothing repopulates the cache because the loads time out → **metastable failure**: the system stays down after the trigger is gone. Defences, in order of cost:
1. **TTL jitter** — spreads expirations of *different* keys (prevents synchronized expiry after a bulk load or deploy). Doesn't help one hot key.
2. **Single-flight / request coalescing** — within a process, concurrent misses for the same key await one in-flight load:

```python
_inflight: dict[str, asyncio.Future] = {}

async def single_flight(key, loader):
    if fut := _inflight.get(key):
        return await fut
    fut = asyncio.get_running_loop().create_future()
    _inflight[key] = fut
    try:
        val = await loader()
        fut.set_result(val)
        return val
    except Exception as e:
        fut.set_exception(e)
        raise
    finally:
        del _inflight[key]
```
(Note: if no one awaits `fut` after an exception, asyncio logs "exception never retrieved" — handle that in real code.) With N app instances you still get N loads, usually fine.
3. **Distributed lock / lease** — `SET lock:k val NX PX 5000`; winner loads, others wait briefly or serve stale. Adds a failure mode (lock holder dies; TTL on lock covers it).
4. **Stale-while-revalidate / soft TTL** — store `{value, soft_expires}` with a much longer hard TTL. After soft expiry serve the stale value and refresh in the background (one refresher). Best user experience; costs memory and some code. 
5. **Probabilistic early refresh** (XFetch) — each reader may refresh early with probability rising as expiry nears; no coordination needed.

**Cold start.** Cache flushed (deploy, Redis restart, failover) → hit ratio 0% → origin sees 100% load. If steady state is 95% hit, the DB was sized for 5% of the traffic — a 20× spike. Defences: persistent/replicated cache, warm hot keys before shifting traffic, rate-limit/shed at the origin (Day 9), bring up capacity gradually. **Always ask: "what does my DB see if the cache is empty?"** If the answer is "falls over", the cache is no longer an optimization; it is part of your availability story and must be operated as such.

**Cache penetration.** Requests for keys that never exist (bots, bad IDs) always miss. Negative caching with short TTL; Bloom filter for huge keyspaces; validate IDs at the edge.

**Hot keys / big keys.** One Redis node per key slot: a viral key saturates one core (Redis command execution is largely single-threaded). Mitigate with a local in-process L1 with a few-second TTL in front of Redis, or key replication (`k#1..k#8`, read a random one). Large values (MBs) block the event loop and blow network.

**Eviction surprises.** `maxmemory-policy` default in Redis is `noeviction` (writes error when full) unless configured — check your managed provider's default. For a pure cache use `allkeys-lru` or `allkeys-lfu`; don't share an instance between a cache and data you can't lose (queues, rate-limit state).

**Inconsistent reads across layers.** CDN + Redis + in-process each with their own TTL: worst-case staleness is the *sum*, and users see different values on refresh. Document the max staleness per endpoint.

### 2.5 Scale: from 1 node to 1M users
- ~10k–50k QPS: one Redis (with replica for failover) is typically enough; watch p99 latency, memory, evictions, hit ratio per key prefix (put the prefix in your metric label — bounded cardinality, per Day 10).
- Beyond one node's memory/CPU: Redis Cluster or client-side consistent hashing — brings resharding concerns (Day 17) and multi-key ops restrictions.
- Multi-region: caches are local; invalidation across regions is eventual. Prefer short TTLs over global invalidation.
- Add an L1 (in-process, 1–5 s TTL) to kill hot keys; accept 1–5 s of inconsistency across instances.

### 2.6 Connecting to your experience
- **LinkedIn**: pick a case where a cache sat in front of a high-fan-in read (profile views, counts, feed). Story shape: *the cache's hit ratio hid the DB's real capacity; a deploy/failover dropped it and we learned the origin couldn't take the load.* If you don't have this exact story, say what you *observed* and what you *owned*; don't embellish. (Day 19 is where you'll build these properly.)
- **NSE market-data system**: the instrument master/token map and last-tick snapshots are the natural cache-shaped data. Latest tick per symbol: a dict updated by the websocket handler is a "write-through in-process cache" where the feed *is* the invalidation — staleness is bounded by the tick interval, and the real failure mode is **a stale value that looks fresh when the feed dies silently**. This is the same lesson as your ping-loop forensics (pykiteconnect #237): a cache with no freshness signal lies. Fix: store `(value, received_at)` and have readers reject or flag anything older than N seconds.
- **Anti-reconnect-storm gate**: it's the same shape as stampede protection — many actors, one expensive shared resource, coalesce into one attempt with a gate and backoff. Say so explicitly; it shows you see the pattern, not a one-off.

## 3. Exercise (15 min)

**Task:** Write (keyboard, Python, no running Redis needed — use a dict as the fake cache) `SWRCache`, a small in-process cache with:
1. `get(key, loader)` async; soft TTL 30 s, hard TTL 5 min, ±10% jitter on both.
2. Within soft TTL: return cached value.
3. Between soft and hard TTL: return the stale value immediately and trigger **one** background refresh (single-flight).
4. After hard TTL or on first miss: await a single-flight load; concurrent callers share it.
5. If the loader raises and a stale value exists, return stale and log; if none exists, raise.
6. Inject `now()` so tests don't sleep.

Then write 3 tests: (a) 100 concurrent `get`s on a cold key call the loader once; (b) stale-while-revalidate returns instantly and refreshes once; (c) loader failure with stale value present returns stale.

**Done looks like:** ~40–60 lines of implementation, 3 passing tests (pytest + `asyncio`), and a 3-sentence comment at the top stating the max staleness (hard TTL + jitter) and what happens to the DB on a cold start. If you run over, skip (e) of the requirements, but do (a).

## 4. Interview drill (10 min)

**Q1 (0→1). We're a 4-person team; the product page is slow. Do you add Redis?**
<details><summary>Model answer</summary>
Not first. I'd measure: which endpoint, what's p95, is time in the DB, serialization, or an N+1? Usually an index or a query fix gets 10× for an hour of work. Next cheapest is HTTP caching/CDN for anything public, then an in-process cache for small config-like data. I'd add Redis if a specific read is hot, expensive and tolerates staleness — and if we already run Redis for jobs or rate limiting, the marginal cost is low. When I add it: cache-aside, entity-by-ID, TTL as the backstop, delete on write, tight timeout with DB fallback, and a hit-ratio metric per key prefix so I can tell whether it's earning its keep.
</details>

**Q2 (scale). 40k QPS on a celebrity's profile; one Redis node is pegged though the cluster is idle. What's happening and what do you do?**
<details><summary>Model answer</summary>
Hot key: all traffic maps to one slot, so one node's CPU/network saturates while others idle. Add a small in-process L1 with a 1–5 s TTL so each app instance hits Redis at most once per interval for that key — it cuts Redis load by roughly (QPS per instance × TTL). If still too hot, replicate the key across N suffixes and read a random one; invalidate all N on write. Also check value size: a 200KB blob at 40k QPS is 8GB/s, so shrink the payload or serve it via CDN. The trade-off is a few seconds of staleness across instances, which for a profile is acceptable; for something like a price or balance it wouldn't be.
</details>

**Q3 (failure). Redis fails over at peak, and then the database falls over and stays down even after Redis is healthy. Walk me through it.**
<details><summary>Model answer</summary>
Cold cache: hit ratio dropped from ~95% to ~0, so the DB saw ~20× its normal read load. Queries slowed, requests timed out before repopulating the cache, clients retried, and the load kept the system in a degraded stable state — a metastable failure. Recovery: shed load at the edge/origin, serve stale or degraded responses, rate-limit cache-miss loads, and restore gradually, warming the hottest keys first. Prevention: single-flight and a per-origin concurrency limit on misses, stale-while-revalidate, a replicated cache, capacity-testing the DB at zero hit ratio (or at least knowing the number), and a circuit breaker so retries don't amplify. It echoes my reconnect-storm incident: bounded, coordinated recovery beats everyone retrying at once.
</details>

**Q4 (judgment). What would you NOT cache?**
<details><summary>Model answer</summary>
Anything where correctness at the moment of use matters more than speed: balances right after a write, inventory at checkout, authorization decisions with long TTLs (a revoked permission must not live for an hour — short TTL or explicit invalidation), and anything per-user-unique with a low hit ratio, where I'd pay memory and complexity for no gain. I also wouldn't cache before I can measure hit ratio, and I wouldn't use the cache as the only copy of data. And I'd avoid caching complex aggregates keyed on many entities early on, since I can't enumerate their invalidation triggers.
</details>

**Q5. How do you keep cache and DB consistent?**
<details><summary>Model answer</summary>
Strictly, you can't without paying for it; so I define an acceptable staleness per use case. The default: commit to the DB, then delete the key; reads repopulate; a TTL bounds any race (reader loads the old row, writer deletes, reader sets old value). For multi-writer or multi-service setups, publish changes via outbox/CDC and invalidate from the event. For read-your-writes on the writer's own session, bypass the cache or route that user to the primary briefly. If something truly needs strong consistency, it doesn't go in the cache.
</details>

**Common mistakes that sink candidates**
- Saying "I'd put Redis in front" in the first minute with no numbers, no hit-ratio target, no invalidation story.
- Describing only the happy path: never mentioning stampedes, cold start, or "what does the DB see when the cache is empty?"
